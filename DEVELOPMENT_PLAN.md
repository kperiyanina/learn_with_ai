# План разработки LearnWithAI

Документ содержит полный план развития приложения, согласованный в чате проекта «Изучи кодовую базу».

## 1. Цель проекта

LearnWithAI должен помогать пользователю формулировать учебную цель, проходить диагностику, получать персональный план обучения, изучать рекомендованные материалы и отслеживать прогресс.

Ключевые свойства продукта:

- персональные учебные планы;
- адаптация плана на основе прогресса;
- задачи по неделям и дням;
- материалы для изучения;
- аналитика и напоминания;
- безопасное хранение пользовательских данных;
- доступ через веб-интерфейс и API.

## 2. Исходное состояние MVP

На момент составления плана в проекте уже были:

- Streamlit-приложение для создания и просмотра учебных планов;
- генерация плана через Groq API;
- локальный шаблонный генератор;
- SQLite-база с таблицами планов и задач;
- отметка задач как выполненных;
- расчёт общего прогресса.

Основные проблемы исходного прототипа:

- отсутствовали пользователи и авторизация;
- данные не были изолированы между пользователями;
- планы передавались неструктурированными словарями и кортежами;
- отсутствовал API;
- AI-ответы не проходили полноценную бизнес-валидацию;
- не было материалов, диагностики, адаптации, уведомлений и расширенной аналитики;
- не было автоматизированной структуры зависимостей и полноценного набора тестов.

## 3. Целевая архитектура

```text
Frontend
  ├─ веб-интерфейс пользователя
  ├─ авторизация
  ├─ планы и прогресс
  └─ материалы и настройки

Backend API
  ├─ users/auth
  ├─ profiles
  ├─ learning goals
  ├─ plans/tasks
  ├─ progress
  ├─ materials
  ├─ notifications
  └─ AI orchestration

Database
  ├─ users
  ├─ profiles
  ├─ goals
  ├─ plans
  ├─ plan_weeks
  ├─ tasks
  ├─ materials
  ├─ progress_events
  ├─ notifications
  └─ ai_requests

External services
  ├─ Groq или другой OpenAI-compatible AI API
  ├─ email/push-провайдер
  └─ мониторинг и централизованные логи
```

Рекомендуемый стек:

- backend: FastAPI;
- ORM: SQLAlchemy 2.x;
- миграции: Alembic;
- база данных: PostgreSQL;
- валидация: Pydantic;
- авторизация: JWT или защищённые серверные сессии;
- текущий frontend: Streamlit для MVP;
- целевой frontend: React/Next.js или другой отдельный web-клиент;
- фоновые задачи: Celery, RQ или планировщик задач;
- тестирование: pytest и API-тесты FastAPI;
- локальная инфраструктура: Docker Compose.

## 4. Этапы разработки

### Этап 0. Подготовка и стабилизация проекта — выполнен

**Цель:** сделать проект воспроизводимым и подготовить его к дальнейшему развитию.

Выполненные задачи:

- добавлен файл зависимостей;
- добавлен конфигурационный слой;
- добавлен `.env.example`;
- путь к SQLite-базе вынесен в настройку `DATABASE_PATH`;
- включена проверка внешних ключей SQLite;
- модель Groq вынесена в `GROQ_MODEL`;
- AI-клиент создаётся только при фактическом запросе;
- тесты больше не вызывают внешний AI API при импорте;
- добавлено базовое логирование;
- добавлены изолированные unit-тесты;
- `.gitignore` дополнен служебными каталогами тестов и Streamlit.

Результат:

- приложение запускается без `GROQ_API_KEY`;
- ошибка показывается только при попытке использовать AI без ключа;
- текущая функциональность SQLite и Streamlit сохранена.

### Этап 1. Типизированная доменная модель — выполнен

**Цель:** заменить неструктурированные словари и кортежи типизированными объектами.

Выполненные задачи:

- добавлены модели `PlanRequest`, `PlanWeek`, `LearningPlan`, `PlanRecord`, `TaskRecord`;
- добавлена валидация цели, уровня, недель, часов и количества задач;
- добавлена проверка последовательности недель;
- AI-ответ преобразуется в `LearningPlan`;
- проверяется соответствие AI-ответа заданным неделям и часам;
- функции базы данных возвращают типизированные модели;
- локальный генератор переведён на `PlanWeek`;
- Streamlit-интерфейс адаптирован к моделям;
- добавлены русскоязычные сообщения валидации;
- сохранены существующая SQLite-схема и данные.

Отдельно исправлено поведение числовых полей:

- значения вне диапазона не подменяются автоматически;
- поле подсвечивается встроенной валидацией Streamlit;
- при попытке создания отображается русская ошибка;
- AI и сохранение в базу не выполняются при ошибке;
- название цели не может быть пустым или состоять только из цифр.

### Этап 2. Пользователи, авторизация и профили — выполнен

**Цель:** обеспечить персонализацию и изоляцию данных.

Выполненные задачи:

- регистрация по электронной почте и паролю;
- проверка email;
- минимальная длина пароля — 8 символов;
- подтверждение пароля;
- хранение паролей в виде PBKDF2-HMAC-SHA256-хеша с солью;
- вход, выход и пользовательская сессия Streamlit;
- таблицы `users` и `profiles`;
- связь планов с владельцем через `user_id`;
- фильтрация планов и задач по текущему пользователю;
- проверка владельца при обновлении задач и прогресса;
- раздел профиля с именем или названием профиля и email;
- автоматическая миграция текущей SQLite-базы;
- перенос старых планов без владельца первому зарегистрированному пользователю.

Принятое решение:

- уровень подготовки и количество часов не хранятся в общем профиле;
- эти параметры задаются отдельно для каждой учебной цели, поскольку у пользователя могут быть разные уровни и нагрузка в разных областях.

### Этап 3. REST API и модульная структура — выполнен

**Цель:** отделить бизнес-логику от Streamlit и подготовить backend для других клиентов.

Реализованные endpoint-ы:

```text
GET    /health
POST   /auth/register
POST   /auth/login
GET    /users/me
PATCH  /users/me

GET    /plans
POST   /plans
GET    /plans/{plan_id}
GET    /plans/{plan_id}/tasks
GET    /plans/{plan_id}/progress
PATCH  /tasks/{task_id}
```

Дополнительно:

- добавлена Bearer-аутентификация с подписанными токенами;
- добавлена настройка `API_SECRET_KEY`;
- API использует общие модели и валидацию;
- реализована проверка владельца ресурсов;
- добавлена OpenAPI-документация и Swagger UI;
- добавлены зависимости FastAPI и Uvicorn;
- добавлены API-тесты;
- Streamlit сохранён как отдельный способ запуска.

Модульная структура:

- `app.py` — точка входа Streamlit;
- `ui/` — модули интерфейса, сессии, авторизации, профиля, создания планов и списка планов;
- `api.py` — создание FastAPI-приложения;
- `api_schemas.py` — API-схемы;
- `api_dependencies.py` — зависимости и Bearer-аутентификация;
- `api_routes_auth.py` — маршруты авторизации и профиля;
- `api_routes_plans.py` — маршруты планов, задач и прогресса;
- `models.py` — доменные модели;
- `database.py` — работа с SQLite;
- `auth.py` и `api_auth.py` — функции аутентификации;
- `ai.py` — интеграция с AI;
- `config.py` — конфигурация;
- `planner.py` — локальный генератор планов.

### Этап 4. Надёжный AI-сервис — запланирован

**Цель:** превратить прямой вызов Groq в управляемый и проверяемый сервис.

Задачи:

- выделить отдельный `AIService`;
- использовать строгие Pydantic-схемы ответа;
- проверять количество недель, часы, задачи и итоговый проект;
- добавить таймауты;
- добавить повторные запросы при временных ошибках;
- ограничить размер prompt;
- журналировать метаданные без секретов;
- безопасно обрабатывать недоступность провайдера;
- добавить fallback на шаблонный план;
- добавить кэширование повторных запросов;
- сделать возможной замену AI-провайдера без изменения доменной логики;
- добавить rate limit для AI endpoint-ов.

Результат: AI-ошибка не ломает приложение и не создаёт некорректный план.

Результат: пользователь получает не статичный список задач, а адаптивный план.

### Этап 6. Полноценные учебные блоки и материалы — выполнен первый релиз

**Цель:** превратить каждую неделю плана в полноценный учебный блок, а внешние
материалы оставить необязательным дополнением.

Задачи:

- сущность учебного блока с теорией, практикой и тестом;
- генерация теории по теме, задачам, уровню и формату занятий;
- подробная инструкция и ожидаемый результат для каждой задачи;
- сохранение учебного блока в SQLite и повторное открытие без повторной генерации;
- прохождение теории с сохранением статуса;
- тест с проверкой ответов, пояснениями и проходным порогом 70%;
- сохранение всех попыток теста, последнего и лучшего результата;
- возможность перепройти тест без удаления истории;
- отображение прогресса по теории, практике, тесту и дополнительным материалам;
- включение всех недель в знаменатель общего прогресса, даже до первого открытия;
- необязательные внешние материалы с проверкой домена, доступности и соответствия теме;
- удаление дубликатов и отбрасывание нерелевантных рекомендаций;
- понятные состояния генерации и повторная генерация после ошибки.

Результат: пользователь проходит не чек-лист, а полноценный учебный блок:
изучает теорию, выполняет практику, проходит тест и видит сохранённую
статистику обучения.

## 7. Критические замечания

- Реальный `GROQ_API_KEY`, ранее находившийся в рабочем окружении, необходимо отозвать и заменить.
- В `.env.example` должны находиться только имена переменных, без секретных значений.
- Нельзя выполнять внешние AI-запросы при импорте тестовых модулей.
- SQLite подходит для прототипа, но целевая архитектура должна перейти на PostgreSQL.
- Все ресурсы API должны проверять владельца.
- AI-ответы должны проходить схематическую и бизнес-валидацию.
- Ошибки внешних сервисов должны журналироваться безопасно и отображаться пользователю понятным сообщением.
- Любые дальнейшие изменения должны сохранять запуск Streamlit и FastAPI.
